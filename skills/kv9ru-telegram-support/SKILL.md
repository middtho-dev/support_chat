# KV9RU Telegram Support

Работай в репозитории `/root/support_chat`. Сначала прочитай его `AGENTS.md`:
он определяет ветки, проверки, публикацию и production. Этот skill не добавляет
разрешений на отправку сообщений, развёртывание или удаление переписки;
проверяй уже предоставленный пользователем объём полномочий.

## Продуктовая модель

- Основной режим — `dialog`: одна Rich-карточка открытого обращения в основном
  личном чате оператора. Темы — только явно выбранный режим отката `topics`.
- Стартовая панель администратора — отдельное одно обновляемое сообщение.
  Разделы меню редактируют его на месте. Не дублируй счётчики одновременно
  длинным текстом, списком и нижней клавиатурой; рядом с действием давай лишь
  сведения, необходимые для выбора. Очистку и редкие действия убирай в сервисный
  раздел. Сохраняй подтверждение очистки и актуальную привязку панели к оператору. Явный
  `/start` переиздаёт панель для восстановления после ручного удаления: Telegram
  может разрешать боту редактировать сообщение, скрытое лишь у пользователя.
  Обычная навигация и `/queue` сохраняют текущий message ID; подтверждённое
  «message to edit not found» должно сбрасывать устаревшую привязку.
- Для кнопок внутри Rich используй проверенные по официальной Bot API схеме
  `InputRichBlockButtons` / `RichMessageButton`, а не выдуманный Markdown-синтаксис.
  У `InputRichMessage` выбирай ровно один формат: `blocks`, `markdown` либо `html`.
  Предусмотри рабочие действия обычной inline-клавиатуры при отказе Rich-формата.
- В Rich Markdown одиночный перенос может стать пробелом. Разделяй статус,
  доставку и пояснение абзацами (`\n\n`) или настоящими Rich-блоками.
- Уведомление о новом вопросе и напоминание поднимают ту же карточку; присутствие,
  подтверждения и обновление меню меняют её тихо. Избегай новых служебных сообщений.

## Доставка и привязка

Сохраняй ответ и скачанный файл до удаления сообщения оператора. Очистка Telegram
выполняется сразу после сохранения и не блокирует доставку клиенту. Ответ остаётся
в Workspace и очереди; удаление из Telegram не означает получение клиентом.

Reply и альбомы привязаны к обращению через сохранённые маршруты. Сообщение без
адресата нельзя отправлять последнему выбранному клиенту по неявному состоянию.
Сохраняй атомарное назначение и запрет ответов в чужие/закрытые обращения.
Клиент получает обычный ответ без операторской цитаты маршрутизации.

Веб-подтверждение — получение данных браузером, не прочтение человеком. Считай все
ручные ответы без подтверждения; у Telegram-клиента показывай отправку, очередь и
ошибки API, не выдумывай прочтение или онлайн-статус. Присутствие веб-клиента —
heartbeat видимой вкладки с таймаутом и учётом нескольких вкладок, а не просто
открытый Socket.IO. Позднее подтверждение не должно удалять новую подсказку.

Закрытие любым путём убирает известные сообщения обращения через сохранённую
очередь. История и файлы Workspace сохраняются. Запреты Telegram на удаление
старых сообщений учитывай отдельно; не объявляй полную очистку, если API отказал.

## Карта кода и проверок

- `src/telegram-admin-menu.js`: стартовая панель и native Rich-кнопки.
- `src/telegram-private.js`: callbacks, выборка очередей, Rich-транспорт, клиентская доставка.
- `src/telegram-support-dialogs.js`: карточки, сохранённые маршруты, обновления,
  уведомления и очистка. `src/telegram-support-inbox.js` — прежняя схема для отката.
- `src/support-delivery-status.js`, `src/customer-presence.js`, `src/server.js`,
  `public/js/app.js`: статусы, аутентифицированный heartbeat и веб-подтверждения.
- `test/telegram-dialogs.test.js`, `test/telegram-dialog-state.test.js`: основной
  режим; `test/telegram-private.test.js`: существующие callbacks и откат `topics`.
- `README.md`, `DEPLOY.md`, `docs/telegram-webhooks.md`: эксплуатационные контракты.

Для меню проверяй реальные outgoing payload: callback каждой кнопки, счётчики,
взятие/открытие обращения, возврат домой, обновление того же message ID, отказ
постороннему оператору и безопасный fallback. Ошибка транспорта не доказывает
отсутствие Rich API; не повторяй отправку другим способом после неоднозначного
сетевого сбоя. Отделяй отказ конкретного Rich-блока от отключения всего Rich.

Запускай проверки из `AGENTS.md`. При изменении клиентского HTML/CSS/JS выполни
предписанный аудит на изолированном стенде и просмотри снимки диалогов/экранов.
Тестовый бот и снимок базы не должны иметь production-ключей и сетевой доставки.
Если проверялась только структура payload, прямо сообщи, что отображение в
настоящем Telegram-клиенте ещё не проверено.

Официальные схемы при работе с Rich:
[InputRichMessage](https://core.telegram.org/bots/api#inputrichmessage),
[RichMessageButton](https://core.telegram.org/bots/api#richmessagebutton),
[InputRichBlockButtons](https://core.telegram.org/bots/api#inputrichblockbuttons).
Проверяй их актуальность перед введением новых типов блоков/кнопок.
