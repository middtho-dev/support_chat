# FRP — самостоятельный инструмент мультитула

Чат в корне репозитория и `tools/frp` — **два независимых приложения**. У FRP отдельные процесс, Docker Compose, секрет входа и том данных. Он не импортирует код чата, не использует SQLite/Telegram и не требует установки зависимостей чата. Команды `setup.sh`/`update.sh` в корне относятся только к чату.

## Запуск на Linux с Docker

```sh
cd tools/frp
cp .env.example .env
# Задайте FRP_ADMIN_TOKEN: случайный секрет длиной не менее 24 символов.
docker compose up -d --build
```

Панель слушает `127.0.0.1:7400`. Опубликуйте её через существующий HTTPS reverse proxy **отдельным виртуальным хостом**, направленным на этот адрес. Можно использовать `routers.kv9.ru` для HTTPS панели и тот же домен с TCP-портом 7000 для устройств. Для локальной проверки без proxy откройте `http://127.0.0.1:7400`.

Вход: отдельный `FRP_ADMIN_TOKEN` из `.env`. Ключ хранится в памяти страницы до выхода/перезагрузки. Токен подключения устройств генерируется автоматически и отличается от ключа панели.

Нажмите **Установить FRP**, затем **Включить**. Приложение скачивает последний стабильный официальный релиз с GitHub для своей ОС/архитектуры, проверяет SHA-256 из GitHub release metadata, извлекает только frps и создаёт TOML. Для установки нужны исходящий HTTPS к GitHub и `tar` (есть в образе). Поддерживаются x64 и arm64. Обновление выполняется той же кнопкой при остановленном FRP.

## Подключение устройств

- По умолчанию: `routers.kv9.ru:7000`. Домен должен указывать на публичный IP машины с FRP; DNS-проксирование HTTP для подключения frpc не подходит.
- Разрешены TCP/UDP-порты 2000–65535 за исключением порта подключения, внутреннего dashboard, панели и `FRP_RESERVED_PORTS` (по умолчанию 3000,3001).
- В firewall разрешите TCP 7000 и конкретные TCP/UDP-порты сервисов. Панель не изменяет firewall или DNS автоматически.
- В панели раскройте пример `frpc.toml`, скопируйте на устройство, задайте уникальное имя, localPort и свободный remotePort. Запустите frpc на устройстве.
- FRP API автоматически сообщает о клиентах: панель показывает имя/ID, IP, состояние и связанные TCP/UDP-порты. Устройства видны даже без туннелей. Идентичность определяется клиентом FRP, а не аппаратным MAC; старые клиенты без стабильного clientID могут создавать новые записи после переподключения.
- Ниже отображаются все TCP/UDP-туннели отдельными строками; рекомендуем имена `router-01-ssh`, `router-01-web`. Неактивные клиенты и туннели остаются в истории (до 10 000 записей каждого вида), включая после перезапуска. «Онлайн» означает регистрацию в FRP, а не проверку доступности локального сервиса.
- Обновление состояния каждые 5 секунд; при сбое API состояние отмечается как неизвестное.

## Независимое управление

```sh
# Из tools/frp: эти команды никак не управляют чатом
docker compose stop
docker compose up -d --build
docker compose logs --tail=100
```

FRP запускается автоматически вместе со своей панелью, если раньше был включён. Кнопка «Выключить» сохраняет выключенное состояние. При аварийном завершении frps панель показывает ошибку, повторный запуск — кнопкой «Включить». Данные и бинарный файл находятся в отдельном томе `frp-data`; не удаляйте его при обновлении.

Без Docker: Node.js 20+, `FRP_ADMIN_TOKEN` в окружении, затем `node tools/frp/server.js`. `.env` при таком запуске не подгружается автоматически; используйте `node --env-file=tools/frp/.env tools/frp/server.js`. Данные по умолчанию в `tools/frp/data`, путь меняется через `FRP_DIR`. Веб-порт: `FRP_PANEL_PORT`, адрес: `FRP_PANEL_HOST`. FRP требует отдельного supervisor для запуска панели после перезагрузки машины (например systemd).

Конфигурация и секреты записываются вне публичного каталога с ограниченными правами. Внутренний dashboard FRP использует случайный пароль и слушает только loopback. Панель должна быть доступна по HTTPS при удалённом использовании.

Проверка: `npm run check` и `npm test` из `tools/frp`.
